## The navigation assert, fixed

Tapping `#15545` inside a **pull request** comment threw
`'!keyReservation.contains(key)'` (M-C §6.2), and so did the pull request page's "Linked work
items" row. The cause is not the mention code: go_router keys a shell route's page by the route's
own identity, so pushing a location that lives *inside* the project tab shell from a page that is
itself *over* the shell asks one navigator to hold two pages with the same key. The pull request
detail page and its file diff are the only such origins — the Activity feed, the search page and
the work item page all push from somewhere the shell is not already on the stack.

The fix is a second route for the same page, `Routes.workItemStandalone` →
`/a/:account/orgs/:org/projects/:project/work-item/:id`, declared **outside** the tab shell and
used only by those two pages. Everything inside the shell keeps using `Routes.workItem`, so the
Work tab, search, a `#123` in another work item comment and the pushed notification deep links all
land exactly where they did, dock and all; only a work item opened from a pull request now arrives
as a plain page over it, like the pull request itself. Verified on the simulator: `#15545` in a
pull request comment opens the work item and Back returns to the pull request, on the Comments tab
and at the same scroll position.

## Return on iOS

M12 binds Return to "pick the highlighted row" through `Shortcuts`. On the iPhone with a hardware
keyboard that binding **fired and was then undone**: iOS's text input system had already turned
the key into an inserted newline computed from the text as it was *before* the pick, and that
editing state arrived after the token had been written and overwrote it. The field ends up with a
broken line and no mention — the worst of both.

`MentionField` now recognises that stale insertion (the exact value it replaced, plus one newline
at the caret it had) and puts the pick back, tokens and all. A plain newline typed while the list
is open picks too, and a newline typed with the list closed is left alone. Verified on the iPhone
and on the iPad: Down, Up, Return inserts `@Kelly Kamm ` with no line break.

## A stale name map

A mention posted on a page whose earlier comments named nobody drew as **`@someone`**: the names
behind `@<guid>` are looked up from the threads the page has read, and reloading the threads after
a write did not re-run the lookup. Both pull request pages now do. The work item page is not
affected — its comments are HTML and carry the name in the anchor.
