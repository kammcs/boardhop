# React Native / Expo + Entra ID Broker Auth — Deep Re-Check, and a Cross-Platform Stack Survey

**Date of research:** 2026-09-10
**Scope:** Third-party Azure DevOps mobile client (iOS + Android, phone + tablet; Kanban boards, rich-text work item editing, PR code diffs, push notifications).

---

## Executive summary

The re-check does not change the prior conclusion — it hardens it. As of September 2026:

- **There is still no maintained, production-grade way to get native MSAL broker authentication in React Native or Expo.** Every community wrapper that ever existed is either formally archived, abandoned by its author with an explicit "please use the other one" note, or a single-project fork whose maintainers say outright they will not support it for outside use. `react-native-app-auth` (Formidable Labs) is the one actively-published, healthy-looking package in this space (v8.4.1, published 2026‑07‑06, ~79k weekly downloads), but it wraps **AppAuth**, not MSAL — it gets you an OAuth2/OIDC browser-based login, not broker SSO, Conditional Access device compliance, or Intune-managed-browser support.
- **Microsoft has never shipped and still has not shipped an official MSAL for React Native.** The closest artifact, `msal-react-native-android-poc` in the AzureAD GitHub org, is explicitly labeled a proof of concept, is Android-only, and was last published roughly six years ago. Microsoft Q&A threads through 2025–2026 consistently answer "there is no official MSAL React Native SDK" and point people either to `react-native-app-auth`/AppAuth-based flows (no broker) or to writing a native module yourself against MSAL iOS/Android.
- **The underlying native SDKs are healthy and current** — MSAL for Android is at v8.4.2 (published 2026‑08‑21) and MSAL for iOS/macOS is at v2.15.0 (published 2026‑08‑20) — so a hand-rolled Expo Module wrapping them is technically sound; it is a real, boundable engineering task (roughly 3–6 weeks for a competent mobile/native engineer to get broker + Conditional Access + Intune-compatible auth working on both platforms, plus ongoing SDK-bump maintenance), but nobody has open-sourced a finished, maintained version of it. A few partial/abandoned attempts exist (e.g., `Archimedes4/expo-msal`, archived since April 2024) but none are usable as-is.
- **There is no official (or even semi-official) Intune App Protection Policy / App SDK support for React Native.** Community bridges exist (e.g., `react-native-ms-intune-mam`) but are tiny, essentially unmaintained, and Microsoft's own GitHub issue threads on the iOS/Android Intune SDK repos have open, unresolved "add React Native support" requests going back years.
- Net effect for Part A: **React Native/Expo remains the weakest option specifically for the broker + Intune requirement**, and that gap can only be closed by committing real engineering time to a custom native module — there is no shortcut package to reach for.
- Part B verdicts in one line each: **Kotlin Multiplatform + Compose Multiplatform** is now genuinely production-credible (Compose for iOS went Stable in CMP 1.8, May 2025) and is the strongest alternative to native twins for this app. **Capacitor/Ionic** has a real, native-MSAL-wrapping broker-capable plugin ecosystem (better than React Native's, somewhat surprisingly) but inherits WebView UI performance limits for diff-heavy screens. **Uno Platform** has first-class, Microsoft-blogged MSAL.NET integration and helper wiring for broker scenarios; **Avalonia**'s mobile target is still explicitly beta. **Native SwiftUI + Jetpack Compose twins** remain the only path with zero authentication or Intune compromises, at roughly double the UI implementation cost. **Tauri 2 mobile** is explicitly not recommended for anything requiring enterprise broker auth — its WebView has no OS browser session and no supported custom URI scheme for Entra ID redirects.

**Overall reading of the table:** every option that actually wraps native MSAL is dead (archived) or explicitly disclaimed by its own maintainer as unfit for outside use. Every option that is *actively* published and downloaded in 2026 (`react-native-app-auth`, `expo-auth-session`, `react-native-azure-auth`) achieves this by **not** using MSAL at all — they get you signed in against the Entra ID v2.0 endpoint via a browser/WebView OAuth2 flow, but none of them can claim broker SSO, device-based Conditional Access, or Intune app-protection integration, because those all require the native MSAL SDK's broker negotiation path (talking to Microsoft Authenticator/Company Portal via keychain groups on iOS or `AccountManager`/broker intent on Android).

### A2. Microsoft's official position (2025–2026)

- Confirmed: **no official MSAL for React Native exists.** The only Microsoft-authored artifact in this space, `msal-react-native-android-poc` (published under the AzureAD GitHub Packages registry, part of the `microsoft-authentication-library-for-js` org), is explicitly a proof of concept, Android-only, and has not been updated in roughly six years.
- Microsoft Q&A threads (e.g., "Am I able to use @azure/msal-react with react native?" and "How to authenticate users with Entra ID OAuth2.0 flow in a React Native App", both on learn.microsoft.com/answers) consistently clarify that `@azure/msal-react` wraps `@azure/msal-browser` and is a **single-page-application (browser)** library — it is not usable inside a React Native runtime (no `window`/DOM), and Microsoft does not offer a substitute.
- Guidance that does exist from Microsoft-adjacent sources routes developers toward either (a) `react-native-app-auth`/AppAuth against the v2.0 endpoint (no broker), or (b) writing a native module against MSAL iOS/Android directly. There is no Microsoft sample repo demonstrating the latter for React Native as of this check.
- **Verdict: unchanged from the prior assessment.** Microsoft's position is de facto "bring your own native module" for React Native + MSAL; it has not shifted in 2025–2026.

### A3. Effort to build a custom Expo Module wrapping MSAL iOS/Android with broker enabled

This is a bounded, well-precedented native engineering task — not a research problem — but it is real work with an ongoing maintenance tail. Breaking it down:

**What you're wrapping (current versions, confirmed via GitHub Releases API, 2026-09-10):**
- MSAL for Android: **v8.4.2**, published 2026-08-21 (`AzureAD/microsoft-authentication-library-for-android`)
- MSAL for iOS/macOS: **v2.15.0**, published 2026-08-20 (`AzureAD/microsoft-authentication-library-for-objc`)

Both SDKs are actively released roughly monthly, which sets the ongoing maintenance cadence for a custom wrapper (periodic bumps, occasional breaking-change migrations — MSAL iOS has had at least one major "2.x" breaking migration in its history).

**Native configuration required (this is the checklist a wrapper module must automate via an Expo config plugin, or the app must configure manually):**

- **iOS:**
  - Keychain sharing group `com.microsoft.adalcache` added under Signing & Capabilities (this is MSAL's default access group for SSO/broker token sharing between apps from the same or cooperating publishers).
  - `LSApplicationQueriesSchemes` in `Info.plist` must include `msauthv2` and `msauthv3` so MSAL can detect and invoke the Microsoft Authenticator / Company Portal broker app via `canOpenURL`.
  - A `CFBundleURLTypes` entry for the `msauth.$(PRODUCT_BUNDLE_IDENTIFIER)` redirect scheme.
  - AppDelegate must forward `application(_:open:options:)` (or the SceneDelegate equivalent) into MSAL's URL handler so the broker callback completes the flow.
  - Note: iOS mandates a single designated authentication broker app — Microsoft Authenticator — for cross-publisher brokered token acquisition; Company Portal handles MAM/Intune enrollment but token brokering funnels through Authenticator.
- **Android:**
  - A `BrowserTabActivity` (`com.microsoft.identity.client.BrowserTabActivity`) declared in `AndroidManifest.xml` with an intent filter matching scheme `msauth`, host = package name, and path = `/<base64 URL-encoded signature hash>` — this signature hash comes from the app's signing certificate and must be generated per build config (debug vs. release) and re-registered in the Entra app registration's Android platform config each time signing keys change.
  - The redirect URI registered in Entra ID must exactly match `msauth://<package-name>/<signature-hash>`.
  - A broker redirect URI (`msauth://<package-name>/<hash>`) must also be registered in the Azure/Entra app registration for the "Mobile and desktop applications" platform.
  - Gradle must be pointed at Microsoft's Maven feed for the Intune/Duo SDK if any Intune/App SDK conditional-launch behavior is added later.
- Both platforms need a `PublicClientApplication` configuration JSON (`msal_config.json`/programmatic equivalent) declaring `authorities`, `broker_redirect_uri_registered: true`, and account-mode settings.

**Surface area to expose from the Expo Module:** `acquireTokenInteractive`, `acquireTokenSilent` (with refresh/expiry handling and `MsalUiRequiredException`/`MSALInteractionRequiredError` fallthrough to interactive), `getAccounts`, `signOut`/`removeAccount`, plus event plumbing for the iOS/Android URL-callback completion handlers. This is a moderate-sized native module — comparable in scope to wrapping any OAuth SDK with async bridging — using `expo-modules-core`'s Swift/Kotlin module APIs (which as of Expo SDK 57 include Swift macros for module/function/record/event definitions on iOS; Android tooling is described as still catching up to the same ergonomics per Expo's own 2025–2026 blog posts on Expo Modules 2.0).

**Effort estimate (unverified — no team has published hard numbers for this exact scope; this is a reasoned engineering estimate, not a sourced figure):**
- A developer competent in both Swift/Kotlin and MSAL's native SDKs: roughly **3–6 weeks** for a first production-ready cut covering interactive + silent token acquisition, broker detection/fallback, sign-out, and multi-account handling on both platforms, plus config-plugin automation of the manifest/plist/entitlements wiring above.
- Add **1–2 weeks** if Intune Conditional Launch / App Protection Policy enforcement is in scope (see A4) — that is a materially larger, separately-SDKed integration.
- Ongoing maintenance: expect to track MSAL iOS/Android releases (roughly monthly cadence observed) and occasional breaking migrations; budget a recurring few days per quarter.

**Evidence of teams doing exactly this in 2025–2026:** thin. The one concrete, named attempt found is `Archimedes4/expo-msal` ("A native MSAL library for expo. This is under heavy development and should be used with caution"), created March 2024 and **archived** by April 2024 without reaching a usable release — i.e., a solo attempt that did not survive to production. No blog posts, conference talks, or maintained GitHub repos from 2025–2026 describing a completed, shipped custom Expo Module wrapping MSAL with broker enabled were found in this search. This absence is itself informative: it suggests either (a) teams needing this have quietly built it in-house without publishing, or (b) most teams facing this requirement have instead chosen native or Capacitor-with-native-plugin approaches (see Part B.6) rather than investing in a bespoke Expo Module — the Capacitor plugin ecosystem (`recognizegroup/capacitor-plugin-msauth`, `hoangqwe159/capacitor-msal-auth`) shows exactly this pattern already done and shipped, which is notable since no React Native equivalent has emerged despite React Native's much larger ecosystem.

### A4. Intune App Protection Policy SDK for React Native

Confirmed: **no official Microsoft SDK, plugin, or bridge exists for React Native.** The Intune SDK team's own stance (per Microsoft Learn and the `ms-intune-app-sdk-ios`/`ms-intune-app-sdk-android` GitHub repos) is that they test and maintain support for native Android and iOS/iPadOS only. Open GitHub issues on the iOS SDK repo requesting React Native support (e.g., "React Native Support," "Add support for React Native") remain open/unresolved across years, which is itself a signal of low prioritization.

Community bridges found:
- `react-native-ms-intune-mam` (Durgaprasad-Budhwani) — wraps the native `IntuneMAMEnrollmentManager` headers; ~6 npm downloads/week, 15 GitHub stars, no PR/issue activity detected in the trailing 12 months (per Snyk Advisor). Effectively dormant, single-maintainer, unverified against current Intune SDK versions.
- Third-party MDM/MAM wrapping vendors (e.g., Appdome) claim they can inject Intune App SDK behavior into React Native (and other non-native) app binaries post-build without source integration — this is a commercial vendor claim, not independently verified here, and introduces a build-pipeline dependency on a third party rather than a code-level SDK integration.
- A blog post ("Integrate Intune SDK to React Native project," nicolasbaptista.com, 2024) documents one engineer's manual integration approach — evidence this has been done ad hoc, but not evidence of a maintained, reusable package.

**Verdict: unchanged.** Intune App Protection Policy support in React Native requires either a from-scratch native-module integration against Microsoft's iOS/Android Intune App SDKs (a nontrivial, Microsoft-unsupported effort layered on top of the MSAL broker module work in A3), a third-party app-wrapping vendor, or abandoning the requirement.

## Part B — Other cross-platform stacks

### B5. Kotlin Multiplatform + Compose Multiplatform

- **iOS stability:** Compose Multiplatform for iOS reached **Stable** in **Compose Multiplatform 1.8.0** (JetBrains blog, May 2025), with JetBrains stating feature parity with Jetpack Compose for popular use cases, type-safe navigation with deep linking, and first-class accessibility (VoiceOver, Full Keyboard Access) as of the 2026 releases. Multiple independent 2026 "is it production ready" retrospectives (Medium/Volpis/kmpship.app) converge on: yes for most product shapes, with some noting residual performance/accessibility edge cases in specific scenarios.
- **Adoption/investment signal:** JetBrains continues active, well-resourced investment (this is their own product); cited production adopters include Sony (Compose Multiplatform) and long-standing KMP-in-production users like Netflix, McDonald's, and Cash App (for shared business logic, not necessarily full Compose UI in all cases — treat the "and Compose UI" framing as partially unverified since the source blends KMP-logic-sharing adopters with CMP-UI adopters).
- **MSAL integration path:** No official Microsoft SDK for Kotlin Multiplatform either, but the architecture is far more tractable than React Native's: an `expect`/`actual` auth interface can directly call the same native MSAL Android SDK (Kotlin/JVM, zero bridging needed — it's already a JVM/Android library) on the Android side, and call MSAL iOS via Kotlin/Native's Objective-C interop on the iOS side. This is meaningfully less bridging work than React Native's JS↔native boundary, since half of the KMP target (Android) can consume the MSAL Android SDK with **no wrapper at all**. A third-party convenience library, `compose-multiplatform-auth` (hyperether, on Klibs.io), already offers a typed Microsoft sign-in result wrapper, evidence the ecosystem is oriented this direction — though its production maturity/broker support is unverified here.
- **Rich text and code editors:** an active, purpose-built ecosystem exists — `MohamedRejeb/compose-rich-editor` (Compose Rich Editor, supports HTML/Markdown, actively released), `Qawaz/compose-code-editor` (syntax-highlighted code display/edit for Kotlin Multiplatform targets), `SnipMeDev/KodeView` (multiplatform syntax highlighting), and `software-mansion/enriched-markdown` (tree-sitter-backed multiplatform markdown with accessibility support). This is a materially better starting point for PR-diff rendering and rich-text work-item editing than anything in the React Native ecosystem's WebView-wrapped alternatives.
- **Hiring:** Kotlin/Compose talent is a smaller pool than React Native's, but overlaps heavily with existing Android hiring markets — likely easier to hire for than Uno/Avalonia (.NET-mobile-specialist) or native-Swift-plus-native-Kotlin dual hiring.

**Maturity verdict for this app: Strong candidate.** This is the most credible alternative to native twins surveyed here — iOS Compose is now Stable (not beta), the MSAL integration story is architecturally simpler than React Native's (no bridge for the Android half), and a genuinely capable rich-text/code-editor library ecosystem already exists for the exact PR-diff and work-item-editing requirements. The main open risk is that **no MSAL wrapper exists yet either** — the same "someone has to write the native auth glue" work applies here as in React Native — but the glue is thinner and the UI-layer payoff is much higher.

### B6. Capacitor / Ionic

- **WebView UI performance:** using `@azure/msal-browser` inside a Capacitor WebView is discouraged by Microsoft (MSAL Browser assumes a real browser session with third-party-cookie and popup/redirect behavior that WebViews often restrict or break) — this matches the framing in the task and is not contradicted by anything found here.
- **Capacitor MSAL plugins with broker support — this is the standout finding of this section.** Unlike React Native, Capacitor has at least one **actively maintained, native-MSAL-wrapping plugin with real broker wiring**:
  - `@recognizebv/capacitor-plugin-msauth` (`recognizegroup/capacitor-plugin-msauth`): 31 GitHub stars, last pushed 2025-04-07, **26 open issues** (signal of real usage and real edge cases, not abandonment — but also signal of unresolved friction). Its README documents the *exact* broker configuration checklist — `com.microsoft.adalcache` iOS keychain group, `msauthv2`/`msauthv3` `LSApplicationQueriesSchemes`, Android `BrowserTabActivity` intent filter keyed on package name + signature hash — i.e., it is a genuine native MSAL wrapper, not an AppAuth/WebView shim.
  - `hoangqwe159/capacitor-msal-auth`: smaller (4 stars, 0 open issues, last pushed 2025-01-21), also documents a `brokerRedirectUriRegistered` option and native MSAL linkage on both platforms.
  - Both are meaningfully more current/complete on the broker-specific configuration front than anything found in the React Native ecosystem, which is a notable asymmetry given React Native's much larger overall community.
- **Performance for large diffs:** unchanged concern — a Capacitor/Ionic app renders its entire UI in a WebView, so a large unified PR diff (hundreds/thousands of lines, syntax highlighting, virtualized scrolling) is subject to WebView DOM/JS performance ceilings rather than native scroll/recycler performance. This is a real risk for the PR-code-diff requirement specifically, independent of the auth story.

**Maturity verdict for this app: Viable for auth, weaker for the diff/editing UX.** Capacitor is, surprisingly, **ahead of React Native** on the specific "native MSAL broker wrapper that exists and is maintained" axis. But the core product requirement of rendering large, fast, native-feeling PR diffs and a rich Kanban board in a WebView is a real architectural tax that a Kotlin Multiplatform/Compose or native approach avoids.

### B7. Uno Platform / Avalonia

- **Uno Platform:** MSAL.NET (the NuGet-distributed `Microsoft.Identity.Client`) works directly, with Uno providing platform-specific helper wiring — Uno's own docs state `.WithUnoHelpers()` handles the platform initializations MSAL needs (e.g., you don't need to manually call `.WithParentActivity()`), and Microsoft/Uno have jointly blogged about MSAL.NET + WebAssembly support. This is a first-party-adjacent, reasonably well-documented integration story — better-documented than either React Native's or Kotlin Multiplatform's MSAL stories, because it's building on .NET's mature, Microsoft-authored MSAL.NET library rather than requiring hand-bridged native SDKs. Broker support specifically (vs. browser-based interactive auth) is referenced in general MSAL.NET/Android broker migration docs but Uno-specific end-to-end broker confirmation was not found — treat broker support on Uno as **plausible but unverified**.
- **UI component maturity / mobile adoption:** general 2026 "MAUI vs Avalonia vs Uno" comparison pieces treat Uno as a mature, real option for cross-platform .NET UI including mobile, but these are third-party blog comparisons, not vendor benchmarks — mobile-specific production case studies for a Kanban+diff-viewer-shaped app were not found.
- **Avalonia:** mobile (iOS/Android) support is explicitly described by Avalonia's own materials as newer than its desktop/Linux support — Avalonia 12 "includes a rebuilt Android backend and strengthened iOS and Mac Catalyst integration" and adopts iOS's scene-based lifecycle, but third-party 2026 comparison pieces (ctco.blog, startdebugging.net) independently characterize Avalonia's mobile targets as **beta-stage** relative to MAUI's iOS/Android maturity, and recommend MAUI over Avalonia specifically for mobile-first products. MSAL.NET itself works fine under Avalonia (same .NET runtime story as Uno), so the auth question is not the limiting factor here — UI/mobile-runtime maturity is.

**Maturity verdict for this app: Uno — plausible niche candidate, unverified on broker specifics; Avalonia — not yet mobile-ready enough for a phone/tablet-first product.** Both would require a C#/.NET-skewed hiring profile, a smaller talent pool than React Native or Kotlin, for a product whose primary requirement (rich mobile UI polish across phones and tablets) is exactly where Avalonia self-describes as still catching up and where Uno's advantage is documentation/integration polish more than proven large-scale mobile deployments.

### B8. Native twin apps (SwiftUI + Jetpack Compose)

- **Auth/Intune completeness:** this is the only option in the survey with **zero compromises** on the stated requirement — MSAL for iOS/macOS (v2.15.0) and MSAL for Android (v8.4.2) are both first-party, actively released, fully broker-capable SDKs, and Microsoft's Intune App SDKs for iOS and Android are likewise first-party and actively maintained (per learn.microsoft.com/intune/app-management/protection). No wrapper, no bridge, no unverified claim — this is Microsoft's fully-supported path.
- **Text editing / diff rendering:** native UIKit/SwiftUI (`NSAttributedString`/`TextKit`, or `AttributedString` in modern SwiftUI) and Jetpack Compose (`AnnotatedString`, `LazyColumn` virtualization, and mature syntax-highlighting libraries in the Kotlin/JVM ecosystem — the same Compose-based libraries cited in B5 apply directly here since this *is* native Jetpack Compose) give the best achievable rich-text editing and diff-rendering fidelity and performance of any option surveyed, with full access to platform text services (spell-check, dictation, accessibility) with no cross-platform abstraction tax.
- **Cost of double UI work:** this is the well-known trade-off — every screen (Kanban board, work item form, PR diff viewer, settings, push notification handling UI) is built and QA'd twice, in two languages, by (typically) two skill-specialized teams or one team context-switching. Relative effort estimate (reasoned, not sourced to a specific benchmark): **roughly 1.6–2.0x** the UI/feature engineering effort of a single well-executing cross-platform stack (Kotlin Multiplatform/Compose Multiplatform in particular, since that option shares business logic and a fair amount of UI code across platforms), for the portion of the app that is UI/feature work — while the *backend, API client, caching, and business-logic* layers can still be shared via other means (OpenAPI-generated clients in both languages, or a shared backend-for-frontend), so the multiplier applies to UI/feature surface, not the whole SDLC.
- **Hiring:** requires either two specialist skill sets (SwiftUI + Jetpack Compose) or one team fluent in both — a real cost, though both skill pools are individually large (mainstream iOS and Android hiring markets).

**Maturity verdict for this app: The safest choice for the stated auth/Intune requirement, at a real and quantifiable UI-cost premium.** If broker SSO, Conditional Access, and Intune App Protection Policy support are hard requirements on day one (not a "nice to have, add later"), native twins are the only option in this entire survey — RN/Expo, Capacitor, KMP/CMP, Uno, and Avalonia all require either building unverified custom glue or accepting a materially weaker auth/compliance posture.

### B9. Tauri 2 mobile

- **Status:** Tauri 2.0 stable shipped October 2024; as of this check the project is on the 2.11 line (2.11.5 released 2026-07-01), with frequent small patch releases indicating active development. Mobile (iOS/Android) support ships via the same Rust core + web-frontend model as desktop, but is explicitly newer and less mature than Tauri's desktop support.
- **Auth viability — this is the disqualifying issue for this app's requirements:** Tauri's WebView has no access to the OS browser's cookie jar/session (it behaves like an isolated/incognito profile), which breaks silent SSO and any enterprise flow relying on an existing signed-in browser session or device registration state. Additionally, Tauri's custom URI scheme (`tauri://`) is **not a supported redirect URI scheme for Entra ID/MSAL** — Entra ID only supports `https:` (production) and `http://localhost` (local dev) redirect URIs for the relevant platform types, and community reports (GitHub discussions on `tauri-apps/tauri` and `AzureAD/microsoft-authentication-library-for-js`) confirm `tauri://`-prefixed redirects fail. There is no Tauri-specific MSAL/broker plugin; the closest available guidance is generic `@azure/msal-browser` usage, which carries the same WebView-authentication caveats as B6's Capacitor concern, compounded by the missing custom-scheme support.
- **General production readiness:** even Tauri-focused 2026 commentary (viadreams.cc) recommends evaluating more mature alternatives (`flutter_rust_bridge`, UniFFI) for production mobile apps "where reliability is critical," and frames Tauri 2 mobile as suitable for "internal tools or early-stage products" rather than a hardened enterprise release target.

**Maturity verdict for this app: Not viable.** Independent of general mobile maturity concerns, Tauri 2 mobile has a specific, currently-unresolved architectural incompatibility with Entra ID's supported redirect URI schemes and with broker/SSO-dependent authentication — this alone rules it out for an Azure DevOps client with the stated enterprise-auth requirements.
